# 更新与本地/线上切换方案

版本：`0.0.19`

## 目标

1. 支持 App 内检查新版本。
2. 支持下载 APK，并拉起系统安装。
3. 支持在 App 内切换 `本地离线版` 与 `线上云端版`。
4. 允许用户输入域名绑定自己的线上部署地址。

## 当前状态

1. `web` 侧已存在 `LOCAL/CLOUD` 的概念，但 `CLOUD` 还没有真实远程仓库实现。
2. 现有数据主要落在 IndexedDB，本地可用，线上不可切。
3. `api-server` 已有 Ktor + MySQL 的后端骨架和一组路由占位，但还没形成完整可用的同步 API。

## 方案一：APK 更新

### 实现方式

1. 后端提供版本接口：`versionCode`、`versionName`、`apkUrl`、`changelog`、`forceUpdate`。
2. App 启动或设置页请求版本接口。
3. 版本过低时弹窗提示更新。
4. 下载 APK 到本地。
5. 调起 Android 安装器完成安装。

### 难点

1. 不能静默安装，必须用户确认。
2. Android 8+ 需要处理“允许安装未知应用”权限。
3. 下载包需要校验，避免包被篡改。
4. 若上架 Google Play，更新策略要改成官方 In-App Updates。

## 方案二：本地/线上切换

### 目标架构

1. `LOCAL`：继续使用 IndexedDB，保证离线可用。
2. `CLOUD`：新增远程仓库，走 `api-server`。
3. `DataModeManager` 根据配置返回不同仓库。
4. 用户在设置页输入域名后，保存为当前云端地址。

### 实现步骤

1. 定义统一的远程 API 协议。
2. 新增 `RemoteRepository`，实现与 `DataRepository` 对齐。
3. 扩展 `DataModeManager`，支持真正切换本地/线上。
4. 增加域名配置、连接测试、绑定保存。
5. 增加同步机制，至少支持首次全量拉取。
6. 再补增量同步和冲突处理。

### 难点

1. 不是单纯加一个按钮，核心难点是同步。
2. 本地和线上都能改数据时，需要冲突解决策略。
3. 域名切换后要处理登录态、缓存、数据归属。
4. 现有 `api-server` 仍需补全实体、表结构、接口实现。
5. 如果只做“切换地址不做同步”，体验会像两个独立系统。

## 落地架构

```text
App
├─ 本地模式
│  └─ IndexedDB / 本地仓库
├─ 线上模式
│  ├─ 用户输入域名
│  ├─ RemoteRepository
│  └─ api-server
└─ 同步层
   ├─ 首次全量拉取
   ├─ 增量上传/下载
   └─ 冲突处理
```

## 建议落地顺序

1. 先做 APK 更新接口和安装流程。
2. 再做云端模式的只读连通。
3. 然后做写入能力。
4. 最后补同步、冲突和域名切换体验。
