# 交易商户与描述字段加密开发文档

## 目标

- 云端 MySQL 中 `transaction.merchant`（商户名称）和 `transaction.description`（交易描述）只保存加密后的密文。
- API 在完成 JWT 与账本归属校验后解密字段并返回原有 JSON 结构，前端显示和既有导入流程无需感知密文。
- 已有明文记录在首次配置密钥并启动后安全迁移为密文。

## 安全设计

- 使用服务器环境变量 `DATA_ENCRYPTION_KEY`，内容为 Base64 编码的 32 字节随机值；密钥只能存在 API 运行环境，绝不发送到浏览器或写入数据库。
- 加密算法为 AES-256-GCM；每个字段使用独立、随机的 12 字节 nonce，并将版本、nonce 与密文序列化为 `enc:v1:<base64url>`。
- GCM 提供机密性和完整性校验。密文损坏或使用错误密钥时，API 拒绝启动/读取，不能静默返回错误数据。
- 未配置密钥时保留既有明文行为并发出明确告警，以避免升级后意外使既有服务不可用；只有配置有效密钥后才启用加密和历史迁移。
- 密钥一旦丢失，已加密字段不可恢复；变更密钥前必须先执行专门的密钥轮换迁移，不能直接替换环境变量。

## 实施步骤

1. 新增服务端字段加解密工具，并对 `DATA_ENCRYPTION_KEY` 的 Base64 和 32 字节长度做严格校验。
2. 将交易的两个敏感字段改为 `TEXT`，以容纳 UTF-8 明文经 AES-GCM/Base64 扩容后的密文；在 MySQL 初始化中兼容已有 `VARCHAR(191)` 列。
3. 在交易写入、批量导入和同步写入的统一入口加密 `merchant`、`description`；在 REST 和同步读取的统一序列化入口解密。
4. API 初始化时，在有效密钥存在的前提下将历史明文交易字段迁移为密文；已加密记录跳过，迁移可重复执行。
5. 增加加密工具和历史值兼容测试；补充 `.env.example`、Compose 与数据库部署说明。
6. 运行前端类型检查、前端测试/构建和后端测试，更新版本记录。

## 验收标准

- 配置有效 `DATA_ENCRYPTION_KEY` 后，新增和历史交易的 `merchant`、`description` 在 MySQL 中均为 `enc:v1:` 开头的密文。
- 正常登录用户看到的商户和描述与加密前一致；未经授权的用户仍无法读取交易。
- 未配置密钥时不产生伪加密数据；配置错误格式或错误密钥时给出明确启动错误，不静默损坏数据。
- 前端包、日志和 API 响应均不包含 `DATA_ENCRYPTION_KEY`。
