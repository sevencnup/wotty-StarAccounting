# Go 后端迁移开发文档

## 目标

将当前 `api-server` 中的 Kotlin/Ktor API 迁移为 Go 服务，在不改变前端、Android 壳、已有 MySQL 数据和公开 API 契约的前提下，降低常驻内存与冷启动成本。最终 Docker API 镜像由 Go 服务提供；Ktor 实现保留至 Go 版本完成全部验收并稳定运行后再归档。

## 已确认的原则

- 本次不是为了修复前端 Turbopack 的 OOM。该问题需独立采用 Webpack、内存限制及分离启动解决。
- 现有 API 的 URL、鉴权方式、请求/响应字段、错误码、分页语义和数据库语义必须兼容，前端不因后端语言变更而改协议。
- 生产 MySQL 数据卷、`.env` 中的密钥和账户数据不可被迁移过程覆盖、清空或重建。
- Go 服务先以并行端口运行，通过契约测试后才允许切换 `docker-compose.yml` 的 API 服务；切换时保留旧镜像作回滚。
- 不自动推送 GitHub、不自动替换当前 Docker 服务，除非用户明确要求部署。

## 技术决策

- 新服务目录：`server-go/`。
- HTTP：Go 标准库 + `chi` 路由；避免重量级框架与隐式行为。
- 数据库：`database/sql` + MySQL 官方驱动；SQL 显式维护，避免在迁移期引入 ORM 映射差异。
- 配置：沿用 `DATABASE_URL`、`DB_USER`、`DB_PASSWORD`、`JWT_SECRET`、`API_HOST`、`API_PORT`、`ACCOUNT_ADMIN_KEY` 等环境变量，不读取或写入密钥到源码。
- 数据库演进：先兼容既有 Ktor/Exposed 表，再将建表和增量变更提取为可重复执行的 SQL migration；禁止在 Go 首版中修改既有业务数据。

## 实施阶段

1. **接口与数据盘点**：枚举 Ktor 路由、认证中间件、DTO、状态码、表和现有测试；为关键 API 建立可重复的契约样例。
2. **Go 基础骨架**：创建模块、配置加载、结构化日志、`/api/health`、MySQL 连接池、统一 JSON/错误响应、优雅退出，并覆盖单元测试。
3. **身份与账户域**：实现注册开关、登录、JWT/会话兼容、当前账户、密码重置与账户设置；使用测试库验证旧密码哈希和令牌语义。
4. **账本核心域**：迁移交易、账单导入、分类、预算、资产、储蓄、贷款和首页汇总接口。每个域完成后以旧 Ktor 响应为基准做契约比对。
5. **数据库初始化与迁移**：补齐全新部署所需的 SQL schema/migrations，并验证空库初始化、旧库升级、重复执行均安全。
6. **并行验收**：Ktor 与 Go 分别运行，自动比对关键接口的状态码、响应结构和计算结果；前端类型检查、测试、生产构建通过。
7. **Docker 切换**：构建带提交版本标签的 Go API 镜像，记录旧容器参数与镜像，先切 API、健康检查 `db:true` 后切 Web；失败自动回滚旧镜像。
8. **收尾**：稳定观察后才删除 Ktor 运行依赖；更新部署文档、版本记录和变更日志。

## 验收标准

- Go 服务启动后在相同环境变量下返回 `/api/health` 的 `{"status":"ok","db":true}`。
- 前端现有 API 调用无需修改 API 地址、登录逻辑或业务字段。
- 身份、账单、储蓄、贷款、资产、预算、导入和汇总的契约测试覆盖核心成功与失败路径。
- 新空数据库可以自动初始化；已有数据库升级不丢数据、不重复插入初始化数据。
- `go test ./...`、前端 `typecheck`、前端测试与生产构建均通过。
- Go Docker 镜像通过健康检查后，内存占用、启动时间与 Ktor 版本进行实际记录比较；没有达到收益不强行切换。

## 本阶段交付边界

本阶段先完成盘点和可运行的 Go 基础服务，不切换正式 Docker，也不删除或修改 Ktor 后端。后续每个业务域独立验证并本地提交，避免一次性重写造成不可定位的账务错误。

- 已完成现有 Ktor 路由、认证边界、12 张表和前端调用面的盘点，并建立接口迁移清单。
- 已新增 `server-go/`：兼容现有环境变量、JDBC MySQL URL、连接池设置、健康检查、版本接口、CORS 和优雅关闭。
