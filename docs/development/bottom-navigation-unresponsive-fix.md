# 底部导航间歇失效排查与修复

## 问题与目标

网页版和 Android App 偶发无法通过底部导航切页，刷新网页或重新进入 App 后恢复。本次先定位点击是否到达导航、路由是否完成以及历史记录和弹层是否干扰，再修复有证据支持的故障路径。

## 实施步骤

1. 检查底部导航、Next 路由、后台恢复、分层历史和 Android 返回策略，记录已有修复的实际覆盖范围。
2. 在浏览器中复现连续切页、路由请求挂起、后台恢复和弹层关闭场景；区分点击遮挡与客户端导航停滞。
3. 按复现结果修复导航及相关生命周期逻辑，保留主标签替换历史和弹层逐层返回行为。
   - 使用静态导出适用的自动预取，排除强制完整预取请求与静态文件不匹配的问题。
   - 首次点击的计时不能被 React 开发模式的效果重放清掉。
   - Android 本地页面恢复时加载对应路由的 HTML，保留 Capacitor 桥接注入。
4. 对实际故障场景执行回归检查、类型检查和必要构建；清理本次临时浏览器及调试进程，保留用户正在访问的预览服务。
5. 记录结论和验证范围，更新版本记录并提交本地仓库。

## 验收标准

- 连续点击和快速切换时，最终进入用户最后选择的标签。
- 后台恢复或路由请求失去响应时，导航不会无限等待，也不要求用户手动退出 App。
- 弹层关闭后不会留下遮挡导航的透明层，正常打开的弹层仍能屏蔽底层操作。
- 标签切换不增加主标签浏览历史，普通链接操作和分层返回保持正常。
- 明确区分已复现并修复的问题和需要真机验证的范围。

## 排查与验证记录

### 已确认的故障路径

1. **静态导出与强制完整预取不匹配。** 底栏原来使用 `prefetch={true}`，同时还有手动预取。当前 Next 16.3.4 的完整预取分支直接请求页面 URL 的 RSC 数据；静态服务器和 APK 只有导出的 HTML、TXT 文件，这类请求拿到 HTML 后会使导航停滞。生产静态产物在没有人为阻断网络时，12 次切页中有 10 次依赖超时恢复。改为 `prefetch="auto"` 后，同样 12 次切页全部由客户端完成，文档请求始终只有首次加载的 1 次。
2. **切页没有完成检测。** 单独挂起路由数据请求时，旧版点击“储蓄”和“设置”均到达链接，但等待超过 13 秒仍停留在“消费”。记账按钮仍能使用，说明此场景并非页面整体冻结。旧恢复逻辑只覆盖离开满一分钟或 BFCache 返回，不能处理刚进入页面时的卡住。
3. **第一次点击与效果重放存在竞争。** 在导航刚挂载时立即点击，React 开发模式的效果重放会清掉刚创建的恢复计时。清理延后一轮微任务，并判断是否已经重新挂载，修复后首次点击也能正常恢复。
4. **Android 默认回退页面不适合多页面静态导出。** Capacitor 将没有扩展名的本地路由统一返回根 `index.html`，该文件实际是登录入口。新增本地路由映射，将 `/app/.../` 交给对应的 `index.html`，仍由 Capacitor 完成桥接注入；使用远程开发服务时不启用此映射。

### 修复后的行为

- 每次点击同步建立 4 秒期限，以 React 已提交的路径确认完成；计时不依赖可能一起挂起的 React 更新。
- 同一目标连续点击不会重复排队或延长期限；切换目标时以最后一次选择为准。
- 超时后替换当前文档进入目标页，不增加主标签历史，也不反复刷新。
- 页面隐藏时暂缓恢复；重新可见后继续检查原期限。网页版离线时保留当前页面，联网后再恢复；APK 可加载本地打包页面。
- 没有待完成切页时，从后台回来不主动刷新，避免打断正在填写的表单。
- 保留链接的新窗口操作、键盘操作、主标签返回策略和弹层分层返回。
